# WorkLoom 账号体系 PRD

> 版本：V2.0 ｜ 2026-09-09
> 适用范围：WorkLoom 全系产品（开源基座 + 仙女座运营平台 + 酒店/电商/视频等各行业版）
> 规模假设：100 万–1000 万家客户企业，单客户 1 人至数千人；民宿、无人酒店、大型集团等多业态并存
> 设计宗旨：**用 AI 运营、运维 AI**——账号体系自身的运营运维由数字员工承担，真人只处理异常升级

---

## 1. 设计原则

1. **真人三种，各进各的门**：客户、伙伴、平台三域分表、分登录、分权限模型，物理隔离；
2. **账号永远平行**：一个真人一个全局账号，与企业的关系是「成员关系」，权限挂在成员关系上；层级只用「集团租户→门店租户」表达，不做子账号树；
3. **默认按业态给模板**：民宿/无人酒店/集团三套预置（角色+审批+委托），客户能改参数，不用从零配置；
4. **规模化的动作必须自助**：注册、激活、邀请、续费、开票、销户全部自助完成，平台真人只碰异常；
5. **跨租户动作双向留痕**：授权方随时看得到被授权方干了什么——信任是卖点；
6. **账号体系自己也是用 AI 运营的**：账号专员数字员工团队负责监控、审计、处置、提醒，真人员工只做裁决。

## 2. 账号域模型

### 2.1 三域总览

```
┌─────────────────────────────────────────────────────────────────┐
│ 客户域（行业版：hotel / ecom / video / …）                         │
│   accounts（全局真人账号）× memberships（账号×租户/工作区，角色+点状权限）│
│   角色：owner（老板）/ manager（店长主管）/ staff（员工）/ readonly（查看）│
├─────────────────────────────────────────────────────────────────┤
│ 伙伴域（partners）                                                │
│   代运营公司 / 托管公司 / 外包团队 / 外部观察者                     │
│   权限来源唯一：客户 owner 签发的授权（grant），随时可吊销           │
├─────────────────────────────────────────────────────────────────┤
│ 平台域（仙女座 workroom-andromeda）                                │
│   platform_operators（真人，MFA 强制，分组授权 + break-glass）      │
│   service_accounts（平台数字员工服务账号，能力白名单，无登录）        │
├─────────────────────────────────────────────────────────────────┤
│ 数字员工（客户域内）：agent，无登录权，行为走围栏+审批，账记所属工作区  │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 数据表

```sql
-- ============ 客户域 ============
accounts(                        -- 全局真人账号
  id, phone UNIQUE, email UNIQUE, wechat_openid UNIQUE,
  password_hash,                 -- argon2id（扫码/验证码用户可为空）
  totp_secret,                   -- 可选二次验证
  status,                        -- active / locked / disabled
  failed_attempts, locked_until,
  created_at, last_login_at
)

memberships(                     -- 账号×租户/工作区成员关系
  id, account_id → accounts, tenant_id, workspace_id,
  role,                          -- owner / manager / staff / readonly
  permissions jsonb,             -- 角色之外的点状授权/收权
  alias,                         -- 本工作区显示名
  quick_pin_hash,                -- 前台快切 PIN（可选，见 §5.4）
  invited_by, joined_at, status
)

auth_sessions(                   -- 会话与令牌
  id, account_id, refresh_token_hash, device_name, device_trusted,
  ip, ua, issued_at, expires_at, revoked_at
)

-- ============ 伙伴域 ============
partners(
  id, name, type,                -- agency / contractor / observer
  contact_account_id → accounts,
  status, created_at
)

partner_grants(                  -- 客户 owner 签发的授权（伙伴权限唯一来源）
  id, partner_id → partners, tenant_id,
  workspaces jsonb,              -- 授权门店清单
  capabilities jsonb,            -- 能力白名单
  constraints jsonb,             -- 时效 / 每日操作上限 / IP 白名单（可选）
  issued_by, issued_at, expires_at, revoked_at, revoke_reason
)

-- ============ 平台域 ============
platform_operators(
  id, account_id → accounts,
  scope_groups jsonb,            -- 分组授权 [{industry, region, cohort}]
  capabilities jsonb,            -- health.view / ticket.handle / credit.adjust / package.deploy / breakglass
  mfa_required boolean DEFAULT true
)

service_accounts(                -- 平台数字员工操作主体
  id, preset_id,                 -- 对应运营岗位
  capabilities jsonb,            -- 岗位能力白名单
  fence_profile,                 -- 围栏档位（只紧不松）
  status
)

-- ============ 横向 ============
approval_policies(               -- 审批人指派矩阵（每工作区一张，业态模板预填）
  id, workspace_id, action_class, fence_level, approver_rule jsonb,
  delegation jsonb,              -- AB 角/休假委托/数字 CEO 授权带
  updated_by, updated_at
)

api_keys(                        -- 客户系统对接密钥（集团 PMS/财务/HR）
  id, workspace_id, name, key_hash, capabilities jsonb,
  rate_limit, last_used_at, expires_at, revoked_at
)

tenant_relations(                -- 集团租户层级
  id, parent_tenant_id, child_tenant_id,
  relation,                      -- direct(直营) / franchise(加盟)
  settlement,                    -- group_pool(集团统付) / self_pay(各自付费)
  created_at
)
```

### 2.3 租户结构与规模分层

| 客户形态 | 结构 | 版本 | 运营分组（cohort） |
|---|---|---|---|
| 民宿/单体店 | 1 tenant + 1 workspace | community/pro | 行业×区域×开通批次 |
| 多店小微（2-10 店） | 1 tenant + N workspace | pro | 同上 |
| 集团 | 集团 tenant → 门店 tenant（加盟可三级：品牌→加盟商→门店） | teams/vpc | 同上+集团标签 |
| 平台方 | 仙女座 tenant | vpc | — |

cohort 标签贯穿全体系：平台授权、灰度发布、SLO 监控、登录安全监控全部按组进行——百万家规模不需要增加运营人力。

## 3. 集团客户

1. **租户两级**：集团 tenant 持品牌资产，门店 tenant 持经营数据；隔离规则按 tenant 不变，集团侧读数走平台汇总投影；
2. **集团标准下发（覆盖层 L1.5）**：在「L0 基座 → L1 行业包 → L2 租户」之间插入集团层——集团下发的围栏参数/话术/服务目录经 draft→canary→active 流水线发布，门店可再覆盖但**只紧不松**（集团定为禁止的，门店不能放开）；
3. **集团角色**：集团管理员（门店租户开通/停用/账号审计）、品牌运营（L1.5 下发）、区域经理（跨门店只读 + 区域内审批）、门店 owner/manager/staff（同单店）；
4. **直营与加盟**：直营门店积分集团统付（集团资金池 → 门店配额下发）；加盟门店各自付费，集团看经营健康度、**不可见流水明细**（隐私边界）；
5. **系统对接**：集团 PMS/财务/HR 通过 scoped API key 接入（工作区级、能力白名单、速率限制、可吊销），密钥调用与真人操作同标准过围栏、同标准留痕。

## 4. 登录模块（完整设计）

### 4.1 页面清单

| 页面 | 说明 |
|---|---|
| 登录页 | 微信扫码（主）+ 手机号验证码（兜底）双通道；平台域入口独立（邮箱+密码+TOTP） |
| 开通页（自助注册） | 扫码 → 选行业版 → 创建企业与首个工作区 → 本人即 owner → 进入行业版体检引导 |
| 激活页 | 一次性激活链接/激活码（渠道批量开通场景），输入后完成注册并归因渠道 |
| 邀请接受页 | 被邀请人扫码/输码 → 完善资料 → 成为对应工作区成员（角色已在邀请时指定） |
| 工作区切换页 | 列出本账号全部 membership（按业态分组），一键切换不重登 |
| 统一待办首页 | 登录后默认页：跨工作区聚合的审批/告警/工单收件箱（见 §6.1） |
| 前台快切屏 | 工作台锁屏 → 输 PIN 换当班人（见 §5.4） |
| 会话与设备页 | 设备列表、信任状态、远程下线（见 §6.2） |
| 异常状态页 | 账号锁定/会话失效/授权过期/被移出工作区的明确提示与申诉入口 |
| MFA 页（平台域） | TOTP 绑定与验证，break-glass 操作前的二次核验 |

### 4.2 核心流程

**首次开通（自助，目标 ≥80% 客户走此路）**
扫码 → 创建账号 → 选行业版 → 命名企业与首店 → 成为 owner → 行业版体检引导（既有的只读快照+快扫流程）→ 决定托管。全程无平台人工。

**渠道批量开通（约 15%）**
渠道商后台上传客户名单 → 批量生成激活码 → 客户输码即开通并绑定渠道归因（计佣依据）。

**平台协助（≤5%，集团/特殊客户）**
开通向导数字员工全程陪跑（资料收集、初始化、首批成员导入），真人只审异常项。

**邀请成员**
owner/manager 在成员管理页输入手机号 → 系统发送邀请（微信/短信）→ 被邀请人接受即入职。角色在邀请时指定，点状权限可后调。

**令牌机制**
access token 2 小时（身份声明沿用现有结构）+ refresh token 30 天（散列入库）；支持单设备踢出、全员强制下线；切换工作区用 refresh token 换发新 scope 的 access token，不重登；密钥表 + kid 轮换；装机版每个客户环境首启生成独立密钥，泄露不出一户。

### 4.3 登录安全防护

- 口令 argon2id；验证码散列存储、一次性、5 分钟有效、同日 5 次上限；
- 防爆破：同账号 5 次失败锁 15 分钟，同 IP 限速；
- 每次登录/异常写不可篡改事件（复用事件账本，审计白得）；
- 登录安全按 cohort 聚合监控（某批次失败率突增 = 批量事故，平台先于客户发现）。

### 4.4 前台快切 PIN（酒店三班倒场景）

前台共用一台电脑，每班扫码不现实：工作台锁屏 → 当班人输 4-6 位 PIN 上岗。PIN 只解锁当前工作台、当前工作区，权限=该成员角色，所有操作记到具体人（交班对账有据）。连续错 5 次锁 15 分钟并通知 manager。无人酒店/民宿默认关闭。

## 5. 权限与审批

### 5.1 两层权限

- **功能权限**：角色 × 能力 × 写操作守卫（未认证 401 / 越权 403 / 越版 403，已上线）；
- **审批权限**：围栏三级（auto/review/block）× 审批人指派矩阵（approval_policies）。

### 5.2 三套业态默认模板

| 动作类别 | 民宿一人店 | 无人酒店 | 集团门店 |
|---|---|---|---|
| 日常执行（回复/内容/查询） | auto | auto | auto |
| 经营敏感（改价/发券/排班） | owner 审（手机一键） | 数字 CEO 按授权带执行，超带转 owner | 店长审，超阈值转区域 |
| 资金相关（退款/赠送/超支） | owner 必审+二次验证 | owner 必审+二次验证（远程） | 区域审，超集团阈值转品牌 |
| 红线（数据导出/删台账） | block，导出需申请 | 同左 | 同左+集团可见记录 |

- 模板随行业包声明，装机按业态预填；客户可调参数，不能改规则结构；
- AB 角/休假委托：委托需 owner 二次确认并留痕；无人酒店的「委托数字 CEO」本质是授权带配置，同一机制；
- 审批通过手势触发二次验证（防代批），审批事件记录审批人+设备+IP；
- **平台永不替客户审批**——客户经营动作的审批权永远在客户手里。

## 6. 登录态「我的」体系（分域个人中心）

### 6.1 客户域：登录后首页 = 统一待办

一人多店是常态（民宿主 2-5 家店、区域经理 30 家店）。登录后默认进入**统一待办收件箱**：跨全部 membership 聚合的审批卡、告警、工单，按店分组、按紧急度排序，点单条进入对应工作区上下文。不切店、不漏事——这是多店客户的第一日常界面。

### 6.2 客户域「我的」页面功能清单

| 分区 | 功能 |
|---|---|
| 个人资料 | 姓名/手机号/微信绑定、各工作区显示名（alias） |
| 我的待办 | 统一收件箱（审批/告警/工单），跨店聚合 |
| 我的权限 | 我在每个工作区的角色与点状权限说明（人话版：「您能做什么、您的什么动作要谁批」） |
| 设备与会话 | 已登录设备列表、信任设备管理、远程下线；异常设备提醒确认（「这是您吗？」） |
| 安全设置 | 快切 PIN 设置/修改、二次验证开关、登录日志（时间/设备/IP/地点） |
| 消息订阅 | 告警/审批/晨报的接收通道偏好（微信服务通知/短信/仅工作台） |
| （owner 专区） | 成员管理（邀请/移除/改角色）、伙伴授权管理、审批矩阵设置、平台操作日志查看、订阅与发票 |

### 6.3 伙伴域「我的」页面

| 分区 | 功能 |
|---|---|
| 我的授权 | grant 清单（哪个客户、哪些门店、什么能力、剩余时效），到期提醒与续约申请 |
| 操作日志 | 我在授权范围内的全部动作记录（与客户看到的一致——双向透明） |
| 工单台 | （contractor）我当前的一次性工单通行证：看单、回传照片、完工打卡 |

### 6.4 平台域「我的」页面

| 分区 | 功能 |
|---|---|
| 我的范围 | 我负责的 cohort 分组、持有的能力清单 |
| 我的操作日志 | 我在客户租户内的全部动作（与客户的「平台操作日志」分区内容一致） |
| 安全设置 | TOTP 管理、设备管理、登录日志 |
| break-glass | 紧急介入申请入口、我的历史介入记录与待写报告 |

## 7. 平台侧账号管理看板

仙女座账号运营中心，五个看板（全部按 cohort 分组、可下钻到单租户）：

| 看板 | 内容 | 主要消费者 |
|---|---|---|
| 账号大盘 | 注册/激活/活跃/留存漏斗，按行业×区域×批次；渠道归因与转化 | 客户成功、增长 |
| 安全看板 | 异常登录、爆破锁定、强制下线事件；批量事故预警（组级失败率突增） | 安全值班 |
| 权限审计看板 | 僵尸账号（90 天未登录）、超权账号（权限>使用量）、长期未用 grant、owner 失联租户 | 账号专员数字员工+真人复核 |
| 伙伴授权看板 | 全平台 grant 台账：签发/到期/吊销率、伙伴动作量排行、异常动作告警 | 客户成功 |
| 会话与密钥 | 活跃会话分布、API key 使用与闲置、密钥泄露嫌疑事件 | 安全值班 |

每个看板的数据源都是事件账本投影，与客户的审计页同源——平台看到的和客户看到的一致，没有对账空间。

## 9. 账号专员数字员工团队（用 AI 运维 AI）

账号体系的日常运营由平台域一支数字员工团队承担，真人员工只做裁决与例外。团队编入平台运营包，与其他运营岗位同标准管理（上岗考试、围栏、反馈枚举、考试院每日回归）。

### 9.1 账号专员（account-steward，负责人岗）

账号域的数字主管：汇总各专员报告、裁决中低风险处置、把高风险事项升级为真人审批卡。每日晨报输出「账号域健康日报」（注册/活跃/安全/审计四格）。

### 9.2 下辖五个专员

| 专员 | 职责 | 核心技能（skills） | 围栏档位 |
|---|---|---|---|
| 登录卫士（login-guard） | 异常登录检测（异地/新设备/爆破/羊毛批量注册）、自动限速与临时锁定、高风险升级 | login-anomaly-scan / brute-force-shield / cohort-baseline | 锁定类动作 review，限速 auto |
| 生命周期专员（lifecycle-clerk） | 邀请/激活/开通全流程自动化、开通失败自愈、渠道批量名单处理、离职批量停用执行 | activation-flow / batch-onboard / offboarding-run | 批量动作 review |
| 权限审计员（permission-auditor） | 每周最小权限复核：僵尸账号、超权账号、闲置 grant、owner 失联租户；产出整改建议卡 | least-privilege-audit / zombie-sweep / grant-review | 只读+建议，处置必审 |
| 伙伴瞭望员（partner-watchman） | grant 全生命周期看护：到期前提醒续签、动作基线监控、吊销执行与通知 | grant-expiry-watch / partner-baseline / revoke-notify | 提醒 auto，吊销 review |
| 密钥保管员（key-custodian） | API key 签发备案、使用基线、泄露嫌疑检测（异地/超速率/非常用能力）、break-glass 全程记录 | key-baseline / leak-detect / breakglass-recorder | 检测 auto，停用 key 必审 |

### 9.3 运营闭环

```
检测（各专员按日/周节奏扫描）
  → 工单（异常自动进仙女座工单流，SLA 计时）
  → 处置（围栏档位内自动执行 / 账号专员裁决 / 真人审批卡）
  → 通知（按 §8 通道触达客户或内部）
  → 留痕（全部动作进事件账本，客户侧可见与其相关的部分）
  → 复核（权限审计员每周复核处置质量，驳回率回流校准）
```

与既有机制的关系：工单走 tickets-flow（SLA 计时由持久化事件总线保障必达）、审批走三手势审批卡、考试走考试院上岗考+每日回归、反馈走受控枚举——账号专员团队复用全部既有纪律，不造新轮子。

## 10. 积分与结算

- 单店/民宿/无人酒店：充值（支付回调→平台复核→事件化入账）/消费（按模型档计量，客户只读）/欠费（降级免费档+提醒，不硬停机）/每夜自动对账（事件投影 vs 支付流水，差异自动工单）；
- 集团直营：集团资金池 → 门店配额下发（集团池为账本第四层投影，门店只见配额进出，事件链不断）；
- 集团加盟：门店自付，集团不可见流水（隐私边界）；
- 伙伴代运营消费：记客户账，客户审计页可按「操作者=伙伴」筛账——代运营花了多少，客户一目了然。

## 11. 数据合规与员工生命周期

- **入职**：邀请制，角色邀请时指定，首次登录即生效；
- **在职**：alias 机制支持工牌名；角色/点状权限变更留痕；
- **离职**：单个移除（owner 操作）/批量停用（集团 HR 对接或名单导入，生命周期专员执行）——移除即时生效，refresh token 同步失效，历史动作留痕保留（审计不可删）；
- **数据权利**：客户数据导出走审批（红线类）；账号注销后个人身份信息按保留期策略脱敏，经营数据归租户；
- **owner 失联**（企业唯一 owner 停用/离职未交接）：权限审计员识别 → 平台工单 → 凭企业证明材料由平台双人复核转移 owner——全程留痕。

## 13. 边界（本期不做）

1. 不做子账号树——层级只用租户层级表达；
2. 伙伴域不做分润/二级代理/伙伴间结算；
3. 不做客户自定义角色编辑器——三套业态模板+点状权限足够；出现新业态势加模板，不加引擎；
4. 不做 C 端客人统一会员账号——客人侧身份是行业包内部事务（如酒店会员体系），不进本账号体系；
5. P0/P1 不做 SSO——P2 按集团客户实际签约需求排期。
